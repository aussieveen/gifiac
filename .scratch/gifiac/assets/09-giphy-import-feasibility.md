# Giphy Import Feasibility — One-Time Migration of Own Uploads into Gifiac

Research date: 2026-08-22. Sources are Giphy's official developer docs (developers.giphy.com) and Giphy's official Terms of Service pages (support.giphy.com), fetched directly. Secondary sources (blog posts, wrapper libraries, community forums) were used only to locate the right official URLs, never cited as evidence.

## 1. Enumerating a user's own uploads

There is **no dedicated "list my uploads" or "my account" endpoint**, and no OAuth / user-login flow at all — the entire API surface (search, trending, random, get-by-ID, get-multiple-by-IDs, upload) is authenticated with a single app-level `api_key` query parameter, not per-user credentials (https://developers.giphy.com/docs/api/endpoint/).

The closest thing to "enumerate a given user's uploads" is a documented feature of the general **Search** endpoint (`GET /v1/gifs/search`): the `q` parameter supports an `@username` syntax — "users can also add the @ sign before a GIPHY username to return content from a specific GIPHY channel" (https://developers.giphy.com/docs/api/endpoint/#search). There is also a documented **Channel Search** endpoint for finding channels by name/username, which can return a channel ID; that ID can then be fed into the Search endpoint's `channel_ids` parameter (accepts up to 5 comma-separated channel IDs) as an alternate way to scope results to one uploader (https://developers.giphy.com/docs/api/endpoint/). Both mechanisms work with a plain (even beta-tier) API key — no elevated auth is needed to query your own username, since it's just a public channel-scoped search.

Caveats on completeness: the docs describe this as search-relevance filtering by channel, not an explicit "return every GIF this user has ever uploaded, guaranteed" contract — there's no documented ordering-by-upload-date or explicit "give me everything" flag. Pagination via `offset` is capped at a maximum of 4999 (https://developers.giphy.com/docs/api/endpoint/#search), which is not a practical constraint for "dozens to a couple hundred" GIFs. In practice, running `q=@<your-giphy-username>` with an empty/broad query and paging through results is the realistic mechanism, and it should be validated once (compare total returned count against what the Giphy website shows for that channel) before treating it as exhaustive.

## 2. Metadata and download URLs

Per-GIF metadata fields documented on the GIF Object schema include: `title`, `slug`, `username` ("the username this GIF is attached to, if applicable"), `source` (page the GIF was found on), `alt_text`, and four timestamp fields — `create_datetime` ("date this GIF was added to the GIPHY database"), `import_datetime` ("creation or upload date from this GIF's source"), `update_datetime`, and `trending_datetime` (https://developers.giphy.com/docs/api/schema/). There is **no tags/caption array** documented on the GIF object — `title` and `alt_text` are the only free-text descriptive fields; there's no keyword-list field to preserve if the user tagged their uploads on Giphy.

The `images` object on each GIF contains multiple renditions. The two relevant to a full-fidelity archival pull, per the schema page (https://developers.giphy.com/docs/api/schema/):

- **`original`**: `url` (the original GIF file), `mp4` (a Giphy-transcoded MP4 of that same original), `mp4_size`, `webp`, `webp_size`, plus `width`, `height`, `size`, `frames`. So the original-quality GIF and an already-transcoded MP4 are both directly downloadable from this one rendition — no separate "original_mp4" top-level key; the MP4 is nested as `images.original.mp4`.
- **`looping`**: video-only — it exposes only an `mp4` field, no still-image `url`.

Other renditions (`fixed_height`, `fixed_width`, `fixed_height_small`, `fixed_width_small`) also carry `mp4`/`mp4_size`/`webp`/`webp_size` alongside `url`; the `downsized*` renditions (`downsized`, `downsized_large`, `downsized_medium`) are GIF-only (`url`, `width`, `height`, `size`, no `mp4`). Notably, **no WebM variant is exposed anywhere** in the schema — Giphy transcodes to MP4 and WebP, not WebM, so a Gifiac import that wants WebM would need to transcode client-side from the MP4/original GIF itself.

## 3. Rate limits

"All API Keys start as beta keys, which are rate limited (100 searches/API calls per hour.) If you need more than 100 API calls per hour you will need to submit an application to upgrade your API Key to production status via your dashboard." (https://developers.giphy.com/docs/api/). For a one-time pull of "dozens to a couple hundred" GIFs, this beta-tier limit is workable: metadata for multiple GIFs can be fetched in a single call via the bulk get-by-IDs endpoint (`GET /v1/gifs?ids=...`) rather than one call per GIF, and even at one call per item, 100–200 items comfortably fits inside one to two hourly windows on a beta key.

Production-tier limits are **not publicly published as a number** — approval requires an application through the developer dashboard, and "if you qualify, a member of our team will reach out via email to discuss pricing" (https://developers.giphy.com/docs/api/tenor-migration/, corroborating https://developers.giphy.com/docs/api/). So there's no documented production rate-limit figure to plan around; only the 100/hour beta figure is concrete.

Separately, the actual media downloads (the GIF/MP4/WebP files themselves) are served from Giphy's media CDN (`media*.giphy.com`) via the direct URLs in the `images` object, not through the rate-limited `api.giphy.com` metadata endpoints — so file downloads are not throttled by the same 100-calls/hour counter, though see Section 4 for why downloading and storing those files at all is restricted by policy regardless of rate.

The general **API Limitations** clause in the API Terms of Service also reserves Giphy the right to change limits at will: "We expressly reserve the right in our sole discretion to limit the number and/or frequency of the API requests" (https://support.giphy.com/hc/en-us/articles/360028134111-GIPHY-API-Terms-of-Service).

## 4. Terms of Service constraints

This is the section that matters most for the "import into local storage" use case, and it's the one place primary sources give an explicit, on-point answer.

**Prohibition on building a local database/archive of GIFs.** Giphy's API Terms of Service, Section 1 ("API License; Restrictions"), states: "You shall not use content you obtain through Giphy's products and services to create a database, directory, or index containing GIFs or digital stickers or to improve, edit, augment or supplement any existing database, directory, or index containing GIFs or digital stickers." (https://support.giphy.com/hc/en-us/articles/360028134111-GIPHY-API-Terms-of-Service). This clause is not scoped to third-party catalog content only — it applies to "content you obtain through Giphy's products and services" generally, and makes no exception for content the requesting user personally uploaded.

**Explicit prohibition on caching/storing media files.** The main API docs page has a "Best Practices" section with a subsection titled "Prohibited Integration Practices" that states directly: "Do not cache media URLs or copies of GIPHY media assets unless your integration has been explicitly approved by GIPHY for media caching and follows GIPHY's required cache revalidation implementation," and separately, under "Caching Requirements for Approved Integrations": "For standard integrations, GIPHY media should be loaded directly from the media URLs returned by the API and should not be cached, proxied, rewritten, or stored by the partner." (https://developers.giphy.com/docs/api/). Unapproved local caching/storage of GIF files pulled via the API — which is the literal mechanism of a Gifiac import — is exactly what this text prohibits for standard (non-partner-approved) API integrations. Getting an exception requires prior written approval from Giphy as a high-scale partner integration, which is not a realistic path for a personal homelab project.

**Ownership of the user's own content is separately confirmed, but doesn't override the above.** Giphy's User Terms of Service, Section 3 ("Content You Contribute"), states: "You are solely responsible for all of the content you contribute to the Services... and as between you and Giphy, you own your User Content," while also granting Giphy "a non-exclusive, worldwide, perpetual, royalty-free... right to use, modify, reproduce, distribute... such User Content... in connection with the Services" (https://support.giphy.com/hc/en-us/articles/360020027752-GIPHY-User-Terms-of-Service). So the user retains underlying copyright ownership of GIFs they personally made and uploaded — but the API Terms' restriction on caching/storing "content obtained through Giphy's products and services" is framed around the *mechanism of access* (the API), not around who owns the underlying IP, and doesn't carve out an exception for "your own uploads." There is no explicit statement anywhere in either ToS document permitting personal, non-commercial backup/export of one's own uploaded content.

**Other applicable clauses:** apps using the API "must be conspicuously labeled" with "Powered by Giphy" attribution (API ToS Section 4), which is awkward but not blocking for a private single-user tool; and the User Terms of Service (Section 6(vi)) separately prohibits using "manual or automated software, devices, or other processes to 'crawl,' 'scrape,' or 'spider' any page of the Services" — this targets scraping giphy.com directly rather than API use, but rules out that alternative import path too (https://support.giphy.com/hc/en-us/articles/360020027752-GIPHY-User-Terms-of-Service).

## Recommendation

**Possible with caveats**

The mechanics all work: a plain beta API key (no OAuth, no elevated tier) can enumerate a user's own uploads via `q=@<giphy-username>` search filtering (or Channel Search + `channel_ids`), each GIF response exposes rich metadata (title, alt_text, create/import/update timestamps) and directly downloadable URLs for both the original GIF and an already-transcoded MP4, and the 100-calls/hour beta rate limit comfortably covers a one-time pull of dozens to a couple hundred items.

The blocking caveat is entirely legal/policy, not technical: Giphy's own developer docs explicitly instruct integrations not to cache or store copies of GIPHY media assets locally without prior written partner approval (https://developers.giphy.com/docs/api/), and the API Terms of Service separately forbid using API-obtained content to build "a database, directory, or index containing GIFs" (https://support.giphy.com/hc/en-us/articles/360028134111-GIPHY-API-Terms-of-Service) — with no documented exception for content the requesting user personally uploaded and owns. A one-time personal export for private archival use is a low-risk, unlikely-to-be-enforced use of the API relative to what these terms are clearly aimed at (competing catalogs, commercial re-distribution), but it is not something the public API/ToS affirmatively sanctions. Secondary caveats: no WebM rendition is exposed (only GIF/MP4/WebP, so WebM would need local transcoding), no tags/keyword field exists on the GIF object (only `title`/`alt_text`), and enumeration via `@username` search is not contractually guaranteed to be an exhaustive listing of every upload.
